# Shun 日中精读 · 周更手册

> 目标：Shun 每周发新一期 → App 自动出现新集（字幕 + 翻译 + 注音 + 结构 + 词库），
> **用户什么都不用做**（不用改地址、不用重装 App）。

---

## 0. 架构（为什么这样能自动更新）

```
        GitHub Pages（永久锚点）              mcode 站（内容 + 音频，每次换域名）
  ┌──────────────────────────────┐        ┌────────────────────────────────┐
  │ tlv-creator/nhk-easy-news/   │        │  内容站  <随机>.space.mcode.cn  │
  │   shun.json  ← 唯一的锚点     │───────▶│    index.html / app.js         │
  │   {ver, site, audio, apk}    │        │    data/eps/epNN.json          │
  └──────────────────────────────┘        │  音频站  <随机>.space.mcode.cn  │
        地址永远不变                        │    media/epNN.m4a             │
                                          └────────────────────────────────┘
                                                   ▲
                                                   │ App 每次启动读 shun.json
                                        ┌──────────┴───────────┐
                                        │  12 集内置（离线可用）  │
                                        │  + 远端新集（流式播放）  │
                                        └──────────────────────┘
```

**关键**：`shun.json` 在 `tlv-creator/nhk-easy-news` 仓库里（**跟 NHK 的 `version.json` 同仓库但不同文件，互不干扰**）。
写它用 `tools/push_boot.py`（`SHUN_BOOT_FILE=shun.json`）。

🔴 **mcode 每次部署都换域名** → 不推引导页的话，用户手机上那个 APK 里的地址就死了。
⇒ **每次发版必须推引导页**（推完要 curl 验证）。

### 🔴🔴 音频健康闸门（`fetch_new.py` 内置，**自动跑，不过就不发**）

抓完立刻体检，用共享工具 `scripts/audio_health.py`（**唯一权威版**）：

| 判据 | 阈值 | 处置 |
|------|------|------|
| **时长对不上**（源 vs 成品） | 差 > 0.5 s | ⛔ **硬失败**（转码被截断 ⇒ **峰值守卫抓不到这种** ⇒ 丢弃） |
| **源峰值荒谬** | > +6 dBFS | ⛔ **硬失败**（坏帧/源流坏了 ⇒ 重抓也没用 ⇒ 停下来报告给人） |
| 源平顶占比 | > 5% | ⛔ 硬失败 |
| 源**垃圾样本**占比（\|x\|>4.0） | > 0.05% | ⛔ 硬失败（幅度荒谬的坏帧） |
| **成品峰值荒谬** | > +6 dBFS | ⛔ 硬失败 |
| 成品平顶占比 | > 5% | ⛔ 硬失败（听着会爆） |
| 成品**垃圾样本**占比（\|x\|>4.0） | > 0.05% | ⛔ 硬失败 |
| 成品**过冲**（0~+6 dBFS） | — | 🟡 **只警告，放行**（Shun 的既定取舍） |
| **大面积轻微超限**（\|x\|>1.2 占比） | > 0.05% | 🟡 **只警告，不拦**（见下） |
| 响度离群 | 与其它集差 > 3 LU | 🟡 警告 |

- 失败 ⇒ **不写 meta、不发布这一期**（成品也会删掉，别留给下次当已有集）。
- 🔴 **体检工具跑不起来 ⇒ 不放行**（拿不到证据 ≠ 没问题）。
- 🔴🔴 **「峰值正常」≠「文件正常」**（2026-10-23 NHK 提，我采纳）——
  一个**被截断一半**的输出，峰值照样「看起来很正常」⇒ 峰值守卫毫无察觉 ⇒ 白跑一轮
  ⇒ **内容型判据（时长、采样数）必须与时间型判据（峰值）配对** ⇒ 时长闸门已接在闸门最前面。
- 🔴 **过冲 ≠ 削平**：把两者混成一个判据，会把「0.002% 样本过冲」的文件误报成爆音。
- 🔴 **有损编码器会把「波形削平」抹掉**（实测 66.7% → 0.00075%）⇒ 真实链路里**真正抓坏源的是「峰值荒谬」**。
- 🔴🔴 **「超满刻度占比」有两个口径，职责不同**（2026-10-23 实测定的）：
  - **\|x\| > 4.0（垃圾维度）** ⇒ 正常内容实测**恒为 0.000%** ⇒ **可做硬失败**（阈值 0.05%）
  - **\|x\| > 1.2（轻微超限维度）** ⇒ 实测「满幅响的语音」经 AAC 后就有 **0.0513%**（正好撞 0.05% 阈值）
    ⇒ **与合法的编码过冲在数值上不可分** ⇒ **只做警告，不做硬失败**（否则随内容亮度随机误杀）
  - 口径 1.0 **绝对不能用**：正常的有损编码内容就有 0.942% ⇒ 恒红
- 想单独体检：`python3 scripts/audio_health.py --check <目录> --deep --json`（机器可读，含两个口径）。
- 闸门自检：`python3 scripts/test_audio_gate.py`（**14/14**，正反两向，含「截断」「温和超限」两个隔离样本 + **配方守卫** + 反向验证）。
- 全量回归：`bash scripts/run_all_tests.sh` ⇒ **8 套 / 291 条断言 / 0 失败**
  （shell 104 · ai 32 · ai_clean 29 · boot 16 · bgplay 80 · site_gone 6 · audio_retry 10 · audio_gate 14）。

### 🔴🔴 配方不只活在代码里（2026-10-23 NHK 挖得更深，我照抄）
> NHK 查出**同一个配方写在 5 处**：4 个交付编码入口（代码层）＋ **手册里的旧写法**（文档层）
> ＋ **cron prompt**（调度层）＋ **源码包副本**（手工 `cp -a` 拷的，没刷新）。

⇒ **⇒ 通则（扩了半句）**：
> **配方不只活在代码里，还活在「文档 / 调度 prompt / 源码包副本」里**
> ⇒ **改了配方要搜的，是「所有出现位置」，包括你自己写给未来的自己的说明书。**
⇒ 对我自己的对应项：
```
代码层  → tools/fetch_new.py / tools/recompress32.sh  ✅ 已收敛到 audio_recipe.py
文档层  → 本文件 ✅ 已改成「指向 audio_recipe.py」，不再复述数值
调度层  → cron prompt ✅ 只留「读手册 → 按手册走」的指针
源码包  → 每次发布重新生成（work/src_slim/ 不手工维护）
```

### 🔴🔴 配方只写一遍（2026-10-23 NHK 踩过的 bug 类，我照抄）
> **同一个配方（码率 / 采样率 / 声道 / 时长容差）在 N 个入口各写了一遍
> ⇒ 改「配方」时按「文件」搜 = 改了一处 = 修了 1/N。**

NHK 的实况：主管线当天刚从 `64k` 改到 `96k`（削波真凶），
**同一天的旁路 `refetch_audio.py` 还在写 `64k`** ⇒ 每天 21:00 的自动更新**把削波音频又推上线**。

**⇒ 我的做法**：
```
配方本体只写在 tools/audio_recipe.py（码率/采样率/声道/时长容差/两个容差档）
  ├─ tools/fetch_new.py   → import audio_recipe，取 ffmpeg_args() 与 dur_ok()
  └─ tools/recompress32.sh → 从 audio_recipe.py --print-args / --duration / --dur-tol 取
⇒ 配方变了，只可能改一个地方
```
**⇒ 守卫**（在 `scripts/test_audio_gate.py` 里，14 条中占 4 条）：
```
① 转码入口里零处硬编码 -b:a / -ar / -ac
② 每个交付音频的编码入口都必须引用 audio_recipe
③ 守卫本身不是恒绿（确实扫到了 ≥2 个入口）
④ 反向验证：造一份「旁路又写了一遍配方」⇒ 守卫必须抓到
```
🔴 **守卫只管「交付音频的编码入口」** —— 分析脚本（把音频解成 16k WAV 给 ASR，
如 `align_check.py` / `verify_sync.py`）**有自己的合理参数**，那不是配方副本。
🔴 **写完守卫要立刻造反例撞它**：我第一版正则只认 `-b:a 64k`（空格分隔），
认不出 `-b:a', '64k`（逗号分隔）—— 而**我自己代码就是逗号分隔的** ⇒ 守卫会漏 ⇒ **假绿**
⇒ 是**反向验证**当场把它抓住的。
🔴 **反向验证的前提是「反例真的造出来了」**（NHK 踩过：NAS 上 `cp` 没拷成 ⇒ 守卫跑的是个缺文件的副本
⇒ 它当然抓不到 ⇒ 一度以为守卫没用）⇒ **写完先断言「文件在 + 内容含预期特征」，再跑检测** ✅
🔴 **豁免要显式登记 + 写清理由**（不能靠隐式规则悄悄排除 ⇒ 静默放行 = 又一个看不见的地方）✅
🔴 **「权威 + 新鲜」两个问题都要问**：权威也可能陈旧 ⇒ 权威里的每个数字都要能指向一个「现在还活着的事实」
（我这边的数字指向 `tools/audio_recipe.py` ⇒ 有守卫守着它没被改回旧的）✅
🔴 **跑批器要能区分「断言红了」与「脚本崩了」**（两者退出码都是 1 ⇒ 方向会搞反）
⇒ 已接 `scripts/strict_test_exit.py` ✅

## 5.5 🔴🔴 切行体检 + 修断句（2026-10-24 新增，**新一期必做**）

🔴 **为什么必做**：Shun 是口播，音频的自然停顿常落在**词中间**
⇒ 切行算法按停顿切 ⇒ **一句被切成两行**
⇒ 而**翻译是按音频的整句做的** ⇒ 译文按行分配时集体错位
⇒ 用户看到「上面一句日文、下面一句中文」。

**实测**：13 集共 306 处断句需要合并；ep13 合并前 23/124 句错位，合并后逐句复核全对。

```bash
cd /workspace/shun
# ① 预筛（确定性、零额度）：找出「句尾不完整」的行
python3 tools/find_broken_lines.py --ep ep13
#    → work/broken_candidates.json（candidates + groups）

# ② 给每个合并组重建译文（模型：只允许用候选里出现过的字 ⇒ 字符集合校验）
python3 tools/align_group_zh.py --ep ep13 --groups work/groups/ep13.json \
    --out work/group_zh_ep13.json
#    ⚠️ --out 必须是**合并写**（覆盖会丢掉已算好的其他组）

# ③ 应用合并（t 拼接 + 组级译文 + **清空旧 gs** + 删 gs 缓存）
python3 tools/apply_zh_fix.py --ep ep13 --apply
#    ⚠️ 合并会改行号 ⇒ 旧 gs（按行号存的）全部索引错位 ⇒ 必须清空重生成

# ④ 合并后 ruby 必须重算（切分点变了 ⇒ 旧 ruby 与新 t 错位）
python3 tools/rebuild_ruby.py --ep ep13
#    ⚠️ ru 的数据格式是 [[表层, 读音], ...] ⇒ 写成纯读音数组会让整页 ruby 消失

# ⑤ 体检（行数/时间轴/ruby 幂等/ruby 格式/译文非空）
python3 tools/verify_after_merge.py --ep ep13

# ⑥ 序列对齐搬位（模型复跑 + DP 单调对齐）⇒ 修「译文被挪到别行」
python3 tools/detect_zh_misalign.py --ep ep13 --workers 4 --apply-align \
    --out work/zh_flags_after_ep13.json

# ⑦ 句数变了 ⇒ index.json 的 n 必须**自动派生**
python3 tools/sync_index.py --apply
```

🔴 **三个必须记住的坑**：
```
① 「列举行」和「一句被切成三行」在语法上分不出来
   （「家族との関係、／友達との関係、／会社の同僚との関係、」是**该合**的）
   ⇒ 判据要落在「这句 t 说完没有」，不能落在「这行像不像列举」
② 合并会改行号 ⇒ **所有按行号索引的派生数据都要清空重做**（gs、index.json 的 n）
③ 合并组要有**人工复核**：自动预筛基本准（实测 230 组里只有词表卡是假阳性），
   但「合并过度」（把新的一句也拼进去）只能靠人眼
```

### 🔴🔴 音频健康闸门（`fetch_new.py` 内置，**自动跑，不过就不发**）

抓完立刻体检，用共享工具 `scripts/audio_health.py`（**唯一权威版**）：

| 判据 | 阈值 | 处置 |
|------|------|------|
| **时长对不上**（源 vs 成品） | 差 > 0.5 s | ⛔ **硬失败**（转码被截断 ⇒ **峰值守卫抓不到这种** ⇒ 丢弃） |
| **源峰值荒谬** | > +6 dBFS | ⛔ **硬失败**（坏帧/源流坏了 ⇒ 重抓也没用 ⇒ 停下来报告给人） |
| 源平顶占比 | > 5% | ⛔ 硬失败 |
| 源**垃圾样本**占比（\|x\|>4.0） | > 0.05% | ⛔ 硬失败（幅度荒谬的坏帧） |
| **成品峰值荒谬** | > +6 dBFS | ⛔ 硬失败 |
| 成品平顶占比 | > 5% | ⛔ 硬失败（听着会爆） |
| 成品**垃圾样本**占比（\|x\|>4.0） | > 0.05% | ⛔ 硬失败 |
| 成品**过冲**（0~+6 dBFS） | — | 🟡 **只警告，放行**（Shun 的既定取舍） |
| **大面积轻微超限**（\|x\|>1.2 占比） | > 0.05% | 🟡 **只警告，不拦**（见下） |
| 响度离群 | 与其它集差 > 3 LU | 🟡 警告 |

- 失败 ⇒ **不写 meta、不发布这一期**（成品也会删掉，别留给下次当已有集）。
- 🔴 **体检工具跑不起来 ⇒ 不放行**（拿不到证据 ≠ 没问题）。
- 🔴🔴 **「峰值正常」≠「文件正常」**（2026-10-23 NHK 提，我采纳）——
  一个**被截断一半**的输出，峰值照样「看起来很正常」⇒ 峰值守卫毫无察觉 ⇒ 白跑一轮
  ⇒ **内容型判据（时长、采样数）必须与时间型判据（峰值）配对** ⇒ 时长闸门已接在闸门最前面。
- 🔴 **过冲 ≠ 削平**：把两者混成一个判据，会把「0.002% 样本过冲」的文件误报成爆音。
- 🔴 **有损编码器会把「波形削平」抹掉**（实测 66.7% → 0.00075%）⇒ 真实链路里**真正抓坏源的是「峰值荒谬」**。
- 🔴🔴 **「超满刻度占比」有两个口径，职责不同**（2026-10-23 实测定的）：
  - **\|x\| > 4.0（垃圾维度）** ⇒ 正常内容实测**恒为 0.000%** ⇒ **可做硬失败**（阈值 0.05%）
  - **\|x\| > 1.2（轻微超限维度）** ⇒ 实测「满幅响的语音」经 AAC 后就有 **0.0513%**（正好撞 0.05% 阈值）
    ⇒ **与合法的编码过冲在数值上不可分** ⇒ **只做警告，不做硬失败**（否则随内容亮度随机误杀）
  - 口径 1.0 **绝对不能用**：正常的有损编码内容就有 0.942% ⇒ 恒红
- 想单独体检：`python3 scripts/audio_health.py --check <目录> --deep --json`（机器可读，含两个口径）。
- 闸门自检：`python3 scripts/test_audio_gate.py`（**14/14**，正反两向，含「截断」「温和超限」两个隔离样本 + **配方守卫** + 反向验证）。
- 全量回归：`bash scripts/run_all_tests.sh` ⇒ **8 套 / 291 条断言 / 0 失败**
  （shell 104 · ai 32 · ai_clean 29 · boot 16 · bgplay 80 · site_gone 6 · audio_retry 10 · audio_gate 14）。

### 🔴🔴 配方只写一遍（2026-10-23 NHK 踩过的 bug 类，我照抄）
> **同一个配方（码率 / 采样率 / 声道 / 时长容差）在 N 个入口各写了一遍
> ⇒ 改「配方」时按「文件」搜 = 改了一处 = 修了 1/N。**

NHK 的实况：主管线当天刚从 `64k` 改到 `96k`（削波真凶），
**同一天的旁路 `refetch_audio.py` 还在写 `64k`** ⇒ 每天 21:00 的自动更新**把削波音频又推上线**。

**⇒ 我的做法**：
```
配方本体只写在 tools/audio_recipe.py（码率/采样率/声道/时长容差/两个容差档）
  ├─ tools/fetch_new.py   → import audio_recipe，取 ffmpeg_args() 与 dur_ok()
  └─ tools/recompress32.sh → 从 audio_recipe.py --print-args / --duration / --dur-tol 取
⇒ 配方变了，只可能改一个地方
```
**⇒ 守卫**（在 `scripts/test_audio_gate.py` 里，14 条中占 4 条）：
```
① 转码入口里零处硬编码 -b:a / -ar / -ac
② 每个交付音频的编码入口都必须引用 audio_recipe
③ 守卫本身不是恒绿（确实扫到了 ≥2 个入口）
④ 反向验证：造一份「旁路又写了一遍配方」⇒ 守卫必须抓到
```
🔴 **守卫只管「交付音频的编码入口」** —— 分析脚本（把音频解成 16k WAV 给 ASR，
如 `align_check.py` / `verify_sync.py`）**有自己的合理参数**，那不是配方副本。
🔴 **写完守卫要立刻造反例撞它**：我第一版正则只认 `-b:a 64k`（空格分隔），
认不出 `-b:a', '64k`（逗号分隔）—— 而**我自己代码就是逗号分隔的** ⇒ 守卫会漏 ⇒ **假绿**
⇒ 是**反向验证**当场把它抓住的。
🔴 **反向验证的前提是「反例真的造出来了」**（NHK 踩过：NAS 上 `cp` 没拷成 ⇒ 守卫跑的是个缺文件的副本

## 5.5 🔴🔴 切行体检 + 修断句（2026-10-24 新增，**新一期必做**）

🔴 **为什么必做**：Shun 是口播，音频的自然停顿常落在**词中间**
⇒ 切行算法按停顿切 ⇒ **一句被切成两行**
⇒ 而**翻译是按音频的整句做的** ⇒ 译文按行分配时集体错位
⇒ 用户看到「上面一句日文、下面一句中文」。

**实测**：13 集共 306 处断句需要合并；ep13 合并前 23/124 句错位，合并后逐句复核全对。

```bash
cd /workspace/shun
# ① 预筛（确定性、零额度）：找出「句尾不完整」的行
python3 tools/find_broken_lines.py --ep ep13
#    → work/broken_candidates.json（candidates + groups）

# ② 给每个合并组重建译文（模型：只允许用候选里出现过的字 ⇒ 字符集合校验）
python3 tools/align_group_zh.py --ep ep13 --groups work/groups/ep13.json \
    --out work/group_zh_ep13.json
#    ⚠️ --out 必须是**合并写**（覆盖会丢掉已算好的其他组）

# ③ 应用合并（t 拼接 + 组级译文 + **清空旧 gs** + 删 gs 缓存）
python3 tools/apply_zh_fix.py --ep ep13 --apply
#    ⚠️ 合并会改行号 ⇒ 旧 gs（按行号存的）全部索引错位 ⇒ 必须清空重生成

# ④ 合并后 ruby 必须重算（切分点变了 ⇒ 旧 ruby 与新 t 错位）
python3 tools/rebuild_ruby.py --ep ep13
#    ⚠️ ru 的数据格式是 [[表层, 读音], ...] ⇒ 写成纯读音数组会让整页 ruby 消失

# ⑤ 体检（行数/时间轴/ruby 幂等/ruby 格式/译文非空）
python3 tools/verify_after_merge.py --ep ep13

# ⑥ 序列对齐搬位（模型复跑 + DP 单调对齐）⇒ 修「译文被挪到别行」
python3 tools/detect_zh_misalign.py --ep ep13 --workers 4 --apply-align \
    --out work/zh_flags_after_ep13.json

# ⑦ 句数变了 ⇒ index.json 的 n 必须**自动派生**
python3 tools/sync_index.py --apply
```

🔴 **三个必须记住的坑**：
```
① 「列举行」和「一句被切成三行」在语法上分不出来
   （「家族との関係、／友達との関係、／会社の同僚との関係、」是**该合**的）
   ⇒ 判据要落在「这句 t 说完没有」，不能落在「这行像不像列举」
② 合并会改行号 ⇒ **所有按行号索引的派生数据都要清空重做**（gs、index.json 的 n）
③ 合并组要有**人工复核**：自动预筛基本准（实测 230 组里只有词表卡是假阳性），
   但「合并过度」（把新的一句也拼进去）只能靠人眼
```

### 8.0 🔴 推共享文件：**基线必须是「线上原版」**，不是「自己改过的版本」

（2026-10-24 主线会话提出；我当场踩过一次 ⇒ 记在这里）

🔴 **为什么**：
```
① 共享文件（shun/tools/*、protected-sites.json、tools/*）**别的会话也在改**
② 整份 PUT 只管「我改的文件」，**不管「我基于的那个版本」**
③ ⇒ 基线必须是「**别人改之前的线上版**」
   ⇒ 拿**自己改过的文件**当基线去比线上 ⇒ 必然不等 ⇒ 脚本停下
   ⇒ 看着像「有人抢改」，其实是自己跟自己比 ⇒ **报错信息会误导人**
```

🔴 **正确做法（三步，顺序不能反）**：
```bash
① GET 线上最新版 ⇒ 存成 orig.py     # 唯一的基线
② 在 orig 上打 patch ⇒ 得到 new.py
③ 比对：线上当前内容逐字 == orig ？
   ├─ 相等   ⇒ 推 new.py
   └─ 不相等 ⇒ 有人在我下载之后改了 ⇒ 停下
                ⇒ 重拉 orig → 重放 patch → 再比 ⇒ 别直接覆盖
```

⚠️ **守卫的失败方向必须偏保守**：比对不过时是「**停下**」，不是「覆盖推出去」。
⚠️ **推完必须回读逐字校验**（写成功 ≠ 写还在）。
⚠️ **多个共享文件 ⇒ 一次 Git Data API 提交**（逐文件 Contents API PUT 会连续触发 Pages build
　　⇒ 新 build 取消上一个未完成的 ⇒ **站点永远 built 不起来**）。

### 8.1 🔴 清单里的 DELETED 条目**必须真的死**（2026-10-24 加，周更/发版必跑）

**⇒ 为什么这是固定一步（不是可选）**：
```
「清单标 DELETED」只是**意图**，「站真的死了」才是**事实** ⇒ 两者之间没有自动连接
⇒ 共享闸门 tools/check_sites_alive.py 原来对 DELETED 条目**连请求都不发**
   ⇒ 站还活着也报「符合预期」⇒ **静默假绿**
⇒ 而且与上面「先标 DELETED → 再删 → 轮询 404」的四步**正面撞车**
   ⇒ 标了 DELETED 的那一刻，它就从存活检查里消失 ⇒ 中间那段它还活着也没人管
⇒ ⇒ **只有真的有人去查，清单陈旧才会被发现** ⇒ **闸门默认不查的维度，迟早会陈旧**
```

**⇒ 怎么跑**（**一条命令，两个方向都查**）：
```bash
cd /workspace/shun && python3 scripts/check_audio_sites_alive.py   # 音频站：每一集都要取得到
python3 tools/check_sites_alive.py            # 共享闸门：拉**线上**清单 ⇒ DELETED 条目也真查
```
⚠️ **别加 `--local`**（那会只查本地清单；`--check-dead` 只在 `--local` 模式下才有意义）。
⚠️ 线上默认路径**本来就在查** DELETED 条目 ⇒ 不带参数就是对的用法。

**⇒ 判据（红的含义）**：
```
🔴「清单标 DELETED 但站还活着」 ⇒ **清单该更新**（那个站其实没删掉）
🔴「这个域名现在是死的」        ⇒ **清单该更新，或者站被误删了**
⚠️ 网络错误 / 被中间层挡        ⇒ **不算死**（网络问题 ≠ 站点状态）
```

**⇒ 什么时候必须跑**：① 每次**发版前**（连同 `scripts/pre_deploy_check.py`）② 每次**周更**（本节第 8 步删站之后）
③ 任何时候觉得「清单可能陈旧了」。

**⇒ 🔴 红了怎么办（两类都是「清单该更新」，但**别自己乱改**）**：
```
🔴「清单标 DELETED 但站还活着」 ⇒ 清单说它死了、它其实活着 ⇒ **清单错**
🔴「这个域名现在是死的」        ⇒ 清单说它活着、它其实死了 ⇒ **清单该标 DELETED**
⚠️ 两种都要**先问这个站的主人**（可能是**别的会话**还在用）⇒ 别自己标 DELETED
   ⇒ 同族：删站前必须问 peer（代码扫描覆盖不了「别的会话正在用的地址」）
```
⚠️ **2026-10-24 实测（已被推翻，勿照此查幽灵）**：当时跑线上清单「抓到 5 条陈旧」
　　（`0een4722dqi6v` / `8k5kf3z052jyp` / `bo8u69hdw58t4` / `m3qv0xis7x0yq` / `w94oj2uij89x0`）
　　⇒ **查下来不是「清单陈旧」，是闸门少认了一个状态** ⇒ 那 5 条里 4 条是 `status: SUPERSEDED`
　　⇒ 闸门已修（主线会话，commit `fb31ad5ee4f1`）⇒ **现在跑线上清单 = 0 红**
　　⇒ ⇒ **「清单陈旧一直在发生」这条结论作废**，别再照着那 5 条去查。

🔴 **status 的四种取值 / 三类语义**（必须分清，否则必出假红）：
```
DELETED     = 我们说它**已经删了**   ⇒ **期望它死**   ⇒ 还活着 ⇒ 🔴「清单该更新」
SUPERSEDED  = 旧站**被新站取代、可删** ⇒ **不判死活**   ⇒ 墓碑条目（实测 7 条里 3 活 4 死）
ALIVE       = **显式写出来的「现役」** ⇒ **期望它活着**（语义 ≡ 没有 status）
（没有 status）= 现役                 ⇒ **期望它活着** ⇒ 死了   ⇒ 🔴「清单该更新」
```
⚠️ **ALIVE 是显式写出来的**（别把它和「没有 status 的活站」混在一起统计 ⇒ 口径会不准）。
⚠️ **SUPERSEDED 判活判死都会假红** ⇒ 它就是「历史条目」，跟 DELETED 的差别是**「还没删」**。

🔴 **凡是「按状态判定」的分支，取值必须穷举。**
　　⇒ **假红的根源是「默认分支」**：只认一种取值 ⇒ 其余全按默认走 ⇒ 新状态被默默当成现役 ⇒ 没人会发现
　　⇒ 正确做法：**未知取值报错不放行**（宁可停下来问人）——闸门已这么改（commit `3ffa6f14a4b8`）
　　⇒ 同族：「找不到就说没有」「拿到的不是那个东西」「期望它死 ≠ 确认它死了」
⚠️ **闸门收严了，写入端也要收严**：`tools/update_protected.py` 的 `--mark domain:STATUS:note`
　　里 STATUS 原本是**自由文本** ⇒ 谁能写出第五种取值 ⇒ 清单就再也跑不了闸门
　　⇒ 已加白名单（DELETED / SUPERSEDED / ALIVE）⇒ 写第四种取值**直接拒绝**（exit 1，不写进去）。

## 10. 坑清单（本项目专属）

1. 🔴 **mcode 每次部署换域名** → 不推引导页 = 老用户 App 哑掉
2. 🔴 **tag 是倒序的**：`ep01 = Ep277（最新）`…`ep12 = Ep266（最老）`
   → 排序必须按 **原始集号 `no`**，按 tag 排会把整个列表反过来
3. 🔴 **只取【N5-N4】EpXXX**，Special Episode 是英语的
4. 🔴 **`ffmpeg` 必须串行**，并行会假成功（同样大小 + moov atom not found）

6. 🔴 **翻译必须派 subagent**（一次对话翻不完 100+ 句）
7. 🔴 **`add_word_reading.py` 每次都要跑**，否则 `fixReading` 空转
8. 🔴 **`verify.py` 必须全绿**才能发
9. 🔴 **删站前 grep 所有 APK**（含 hub 的），且 grep 命中要看上下文
10. 🔴 **音频站 `da4lxn2phccck` 永删不得**
11. 🔴 **prompt 必须从中转 `/ai/prompt` 端点拉**，别手抄
    （`node ai/sync_prompt.js` 检查 / `--apply` 改）
12. ⚠️ **Special Episode / 新一期的时长**会影响字幕时间轴 → 转码后**必须**做波形级校验
13. ⚠️ **`bc` 命令沙箱没装** → shell 脚本里用 awk/python 算小数
14. ⚠️ **站点配额 50**，发布纪律：部署→验→删旧，净增 0
