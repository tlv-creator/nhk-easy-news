## 0. 这是个什么项目

NHK「やさしいことばニュース」= 给在日外国人看的**慢速新闻**，每期三件套：

| | 内容 | 特点 |
|---|---|---|
| 慢速音声 | NHK 官方朗读版（每期都有） | 50~70 秒，短句 |
| 易懂版正文 | `easy.html`（每期都有） | **NHK 官方逐字 ruby**（`<ruby>20日<rt>はつか</rt></ruby>`） |
| 普通版書き起こし | `web.json`（**只有电视播过的期才有**） | 新闻稿，敬语书面体，30~155 句 |
| 原速音声 | 电视新闻视频音轨（**只有电视播过的期才有**） | 时长 ≈ 慢速 ×2 |

**产品形态**：照魔卡少女樱 v2.10 的界面做，每个版本有：逐句字幕流（日文全注音 + 简体中文）、
点句弹 92% 大详解面板（①逐词拆解 ②语法说明 ③整句结构）、生词/句型表、7 套主题、后台播放。

```
GET https://news.web.nhk/tix/build_authorize?idp=a-alaz&profileType=abroad&entity=none
    &area=130&pref=13&jisx0402=13101&redirect_uri=…
→ 302 → a.authz.ac1.nhk → cookie z_at（JWT，scope=get:news get:tv，约 12h）
```
- 媒体令牌：`GET https://mediatoken.web.nhk/v1/token` + `Authorization: Bearer <z_at>`
  → `{"token":"exp=…~acl=/*~hmac=…"}`（约 1 小时有效）
- **令牌要拼在 URL 上**：`?hdnts=<urlencode(token)>`
- 全量索引：`https://news.web.nhk/news/easy/news-list.json`（需 z_at cookie）
  → 234 天 / 619 期（字段 `news_id / title / news_easy_voice_uri / news_web_movie_uri / news_web_url`）

`auth.py` 已封装 `get_token()` / `api_get()` / `cookie_header()`。

### 🔴 2.1 音频配方（**唯一权威** = `scripts/audio_recipe.py`，改配方只改那里）

```
交付音频编码：-c:a aac -b:a 96k -ar 48000 -ac 2 -movflags +faststart
   🔴 96k 不是拍脑袋：64k 的 AAC 重建过冲会把波形压扁 ⇒ 削波（实测 13 期里 10 期峰值 +0.6~+2.0 dBFS）
   🔴 1.5 dB 余量只在**一处**扣（响度目标里定义过 ⇒ 滤镜里就不要再减第二次）
原速音响度目标：同期慢速音 − 1.5 dB（容差 0.5 dB）
```

**⇒ 每日管线顺序固定（别自己改顺序，转码那步会把前面的配方抹掉）**：
```
① scripts/repair_all_audio.py   修坏帧（PCM 层；源流自带 51 带 AAC 帧）
② retranscode.py                 96k 重编（原生逐声道峰值守卫 + 时长闸门）
③ scripts/loudnorm_fix.py        原速音对齐（slow − 1.5 dB）
④ scripts/audio_health.py        四维体检（不过就不发）
```

**⇒ 四道体检判据（各管一种坏法，缺一不可）**：
```
① 削平（平顶占比 > 5%）        → 有损链路里基本抓不到，留当兜底
② 垃圾样本（超满刻度 4.0 口径 > 0.05%）→ 抓「幅度荒谬」的坏帧
③ 过冲（峰值 > 0 dBFS）        → 只警告（与合法编码过冲不可分）
④ 时长（|成品 − 源| > 0.5s）    → 抓截断与丢帧（幅度维度完全抓不到的那种）
```
🔴 **三条测量口径的坑**（我自己踩过三次）：
```
· 测峰值必须用**原生逐声道**（`-ac 1` 下混是另一个信号 ⇒ 高 3 dB ⇒ 阈值永远达不到）
· 解码**不要带 `-ar`**（重采样器自己会造出超满刻度样本）
· 超限占比的**口径**是 4.0 不是 1.0（1.0 口径下合法满幅内容就有 0.942% ⇒ 恒红）
```

### 音频下载的四道坎（踩过，别重蹈）
1. **慢速音声**：`https://media.vd.st.nhk/news/easy_audio/<voiceId去.m4a>/index.m3u8?hdnts=<mtok>`
   → `ffmpeg -c copy -bsf:a aac_adtstoasc -f mp4`
2. **原速音声**（电视视频流抽音轨）：
   - HLS 分片 URL **每一片都要单独加 `&hdnts=`**
   - ffmpeg 走 crypto+https 会丢 Referer → 用自建代理 `hls_proxy.py` 补头
   - 密钥 URI 含 `acl=/*` 斜杠 → 代理自己取 16B 密钥下发
   - 音轨探测不到 → 必须 `-analyzeduration 30000000 -probesize 50000000`
3. **媒体令牌 1 小时过期** → 批量脚本每 12~15 期刷新一次（`fetch_fast.py` 已处理）
4. **`ffmpeg` 并行跑会被后台任务掐断** → 产出同样大小的文件 + `moov atom not found`（假成功）→ **必须串行**

## 6. 🔴 踩过的坑（每一个都花过时间）

### 6.1 原生播放器只认绝对 URL
`data/cdn.js` 里是**相对路径** `media/slow/xxx.m4a`。
浏览器会自己补成绝对 URL（网页版正常），但 `MediaPlayer.setDataSource()` 会**当成手机里的本地文件路径** → 必然 prepare 失败。
→ **凡是交给原生播放器的 URL，先 `absUrl()`**：`new URL(u, location.href).href`。
（playAudio / downloadAudio / fallbackToWeb 的 setSrc 都要）

### 6.2 原生桥先判空再启动 Service（静默静音）
`Bridge.playAudio()` 里先 `AudioService.get()`，第一次启动时 Service 的 `onCreate` 还没跑 →
拿到 null 就 return → **什么都不播而且不报错**。
→ 不要用 `get()` 判空，把指令丢给 Service 让它自己在 `onStartCommand` 处理。
→ Android 8+ 必须 `startForegroundService()`，Service 启动后 5 秒内必须 `startForeground()`。

### 6.3 HLS 拼来的 m4a 有坏帧 ⇒ **PCM 层修**，不是「重新编码一下」
🔴 **根因（2026-10-23 查明）**：NHK 慢速音从 **HLS 的 TS 分片**拼出 ⇒ 分片含 **51 带 AAC 帧**（解码器只支持 45 带）
⇒ 解码出**超满刻度的垃圾样本**（实测峰值 **+2.8 ~ +76.9 dBFS**、超限样本 0.004%~0.12%）
⇒ ① 用户听到「啪啪啪」② **Android 平台解码器比 Chrome 严** → 可能整段跳过
🔴 **重抓救不了**（实测重抓 3 次字节完全一致 ⇒ 坏的是源流本身；换落盘方式/直接重编都救不了）
⇒ **修法**：`scripts/repair_audio.py`（PCM 层）
```
找 |x| > 1 的**爆裂簇**（5ms 内的间隔算同一簇）→ 落在静音里置 0 / 落在语音里插值
→ 头room **算出来**不能拍：gain = 目标(−1.5 dB) − 修后峰值
```
⇒ 修完**验四项**：峰值 / 超限占比 / 时长 / **有效语音占比**（内容一点没少才算成功）
🔴 **温和坏帧（峰值只 +2.8 dBFS）幅度统计与合法编码过冲不可分** ⇒ 靠**簇/跳变（时间维度）**抓；
**幅度荒谬那批（+11~+77）靠峰值抓** ⇒ 两者分工，不是二选一。
🔴 编码参数**别在这里写** ⇒ 见 §2.1（唯一权威 `scripts/audio_recipe.py`）

### 6.4 🔴🔴 平台部署会注入悬浮球 + PV 统计脚本（2026-10-24 实测加固）

`website_deploy` 部署时**自动注入**三样东西到 index.html：
```
① <script data-minimax-analytics="minimax-website-analytics-v1"> → POST 到 agent.minimax.cn（PV 统计）
② <div id="minimax-floating-ball"> + 它的 CSS（「Created by MiniMax Agent」）
③ 它的初始化 JS：点球 → window.open('https://agent.minimax.cn/','_blank')
   ⇒ 在 App 的 WebView 里点它 = **把用户整个甩出 App**
```
🔴 **实测结论（2026-10-24，部署前剥 + 部署后实测）**：
> **「部署前把 deploy_site/index.html 剥干净」是无效的** ——
> 平台是**在上传那一刻**注入的（我剥完 → 部署 → 线上 index.html 第 349 行又有统计脚本 + token）。
> ⇒ 源码里剥一次没用（**手册 §6.4 老结论依然成立**），**运行时兜底才是真解**。

⇒ 现在是**三层**：
| 层 | 做法 | 在哪 |
|---|---|---|
| ① 拦截 | head 最前面的 `<script>` 拦 `sendBeacon`/`fetch`（白名单常量 `var BLOCK = 'agent.minimax.cn'`） | 源码，**必须保留** |
| ② 藏 | `#minimax-floating-ball{display:none !important;}` —— **内联**在 index.html（style.css 没加载也挡得住） | 源码 |
| ③ 摘 | 运行时把球和统计脚本**从 DOM 里删掉**（`platformInjectGuard`） | 源码 |

🔴 **③ 的实现要点**：
- 球 id **拆成两段拼**（`'minimax-' + 'floating-ball'`）
  ⇒ 因为剥除脚本的 CSS 正则会在全文找「选择器 + {…}」，
  **连续的 `minimax-floating-ball` 字面量会让它把这段 JS 当 CSS 改坏**（2026-10-24 踩过）
- 脚本放在 body 末尾 ⇒ 跑在平台注入的脚本**之前** ⇒ DOMContentLoaded 时先摘球
  ⇒ 平台的初始化函数拿到 null 会自己 return（它有判空）⇒ **不产生 JS 错误**
- 用 MutationObserver 兜底（8 秒后停止观察）⇒ 万一平台晚点注入也能摘掉

🔴 **剥除脚本（`scripts/strip_inject.py`）**：进 `work/deploy_nhk.sh prepare` 的最后一步
（源站 + deploy_site 各剥一次）⇒ **以后不用记**。
⚠️ 但它只对**源码**有效（平台部署时还会再注入）⇒ **兜底脚本才是主力**。

🔴 **本地加固版修了共享脚本的两个 bug**（2026-10-24 实测踩到，**上游值得同步**）：
```
① 统计脚本的正则只认「script 标签 + data-minimax-analytics 属性」
   ⇒ **注释里写一句**「<script data-minimax-analytics=...>」会被当成注入块
   ⇒ 一路吃到下一个 </script> ⇒ **把中间的正常内容整块吃掉**（我的兜底脚本就这么被吃掉的）
   ⇒ 修：精确匹配平台的属性值 'minimax-website-analytics-v1'
② CSS 重写正则**在全文跑** ⇒ 会扫到 JavaScript 代码 ⇒ 把 JS 改成 CSS 规则 ⇒ **文件语法坏掉**
   ⇒ 修：只对 <style>…</style> 块内的内容做替换
③ 「统计脚本还在」「window.open 还在」两个断言**用字符串全文判定**
   ⇒ 注释/文档里写一句就**永远红**（假红）⇒ 修：断言只看**真的标签**和**可执行代码**
④ 「防误删」特征词清单里加 'platformInjectGuard' ⇒ 兜底脚本被误删时能红
```

### 6.6 手搓 APK 的坑
```
① JDK：apt 源不可达 → 直接下 tarball（华为云 mirrors.huaweicloud.com/openjdk/17.0.2/… 可用）
② 工具链：dl.google.com/android/repository/build-tools_r34-linux.zip + platform-34-ext7_r03.zip
```

### 6.6b 🔴🔴 手搓 APK 的四个「静默」坑（2026-10-23，全部是**不报错**的那种）
```
⑥ 🔴 build.sh 曾经**用 sed 改自己**（把 aapt2 里硬编码的 --version-code 同步成 $NEXT）
   ⇒ 失败时 restore_version 还原了 VERSION / Config.java / AndroidManifest.xml，
     **却没还原 build.sh 自己** ⇒ 脚本里的版本号从此永久漂移
   ⇒ 后果：产物 APK 的 versionCode 与源树对不上，**而包能装能跑，现场看不出来**
   ⇒ 修：aapt2 直接用变量（`--version-code "$NEXT"`）⇒ 版本号只有一个来源
      + 新闸门 scripts/apkchk/check_apk_version.py（产物 == 源树三处，不一致就拒出包）

⑦ 🔴 build 原来在末尾把产物**直接拷进 site/app** ⇒ 「本地构建产物」覆盖了「待上线产物」
   ⇒ 一次失败/半途而废的 build 就把要上线的那份换掉
   ⇒ 而且还往 site/app（= 部署源）里塞 `NHK慢速新闻-精読-v1.x.apk`
     ⇒ 下次 `cp -a site/app deploy_site` 会把它**发到公网**
   ⇒ 修：**build 只出包**（apk/out/signed.apk）；上线是独立动作 `apk/stage_apk.sh`
   ⇒ 顺带把「四份产物」的名字对齐事实（别都叫「发布」）：
        ① apk/out/signed.apk        构建产物（未上线）
```

## 7. 更新一次的完整流程

### ⚠️ 第一步永远是恢复环境
**沙箱会被重置**：`/opt`（JDK / Android 工具链）和 `site-packages`（janome / faster-whisper）都会丢，
whisper 模型缓存（~/.cache/huggingface）也会丢。

`setup_env.sh` 会：装 janome + faster-whisper（阿里云 PyPI 源）、
下 JDK（华为云/中科大/南大任选其一，**apt 装不了**）、下 Android build-tools + platform、
并报告 whisper 模型缓存还在不在（不在的话第一次 ASR 会重下 460MB，
需要 `HF_ENDPOINT=https://hf-mirror.com HF_HUB_DISABLE_XET=1`）。

### 然后
```bash

# ① 抓新一期 + 跑 ASR + 生成工作单（翻译环节交给 subagent）
# 🔴🔴 2026-10-26 修：**先 fetch_batch 再 update.py** —— 顺序反了就**没有音频**
#    · `fetch_batch.py` 出 **文本 + 慢速音**（data/audio/<id>.m4a ← build_site.py 就读这个）
#    · `update.py --all` 只出文本（easy_text / web_text 数组）+ 跑 ASR + 出翻译工作单
#    ⇒ 少跑 fetch_batch ⇒ build_site 拷不到音频 ⇒ **那期会没声音**（静默，不报错！）
#    ⇒ 抓音自证（2026-10-26 实测）：拿**已发布**的 10-23 跑一遍 fetch_batch
#       ⇒ 时长差 0.043s、RMS 包络相关系数 **1.0000**、码率 62k→94k（配方重编 96k）
python3 fetch_batch.py 20 /workspace/nhk/data      # 抓文本 + 慢速音（已存在会跳过）
python3 update.py --all

# ② 把 update.py 打印出来的待翻译工作单派给 subagent
#    （读 work/AGENT_TASK.md / work/KANA_TASK.md / work/SYN_TASK.md）
#    产出：work/out/*.json、work/syn_out/*.json

# ③ 合并 + build + 拷音频 + 重编
python3 update.py --build

# ④ 打包 APK（**只有原生层代码改了才需要**）+ 放进待上线区
#    🔴 顺序：必须在「部署」**之前**，否则新 APK 根本没进这次部署
cd /workspace/nhk/apk && bash build.sh && cd /workspace/nhk && bash apk/stage_apk.sh

#       （落盘 work/pending_site_deletes.txt）⇒ 要有权限的会话执行（详见 §29.1）

# ⑥ 交付：zip（APK + 交付说明）
```

## 8. 增量更新是怎么设计的（重要）

NHK 每天一期，所以**必须能只加新期，不重做全部**。各环节的增量策略：

| 环节 | 增量方式 |
|---|---|
| 抓取 | `fetch_batch.py` 已存在就跳过；`fetch_fast_fill.py` 只针对 build 选中的期 |
| ASR | `run_asr.py`：`data/timing/<id>.json` 存在就跳过那期 |
| 翻译工作单 | `prep_work.py --only-missing`：**只给 `work/out/` 里没有译文的期**生成 |
| 成分块工作单 | `prep_syn.py --only-missing`：同上 |
| build | `build_data.py 0`（0 = 全部）：**只收「翻译完整」的期**，没译完的先跳过 |
| 清理 | build 完自动删掉不再需要的 `subs/*.js` 和 `media/*.m4a`（不删会越攒越多、白占流量） |
| 音频重编 | `retranscode.py` 全量重编（39 个文件约 1 分钟，可接受） |
| 词库/读音 | 全量重建（`build_data.py` 每次都重扫全语料，1 分钟内） |

🔴 **批次划分必须和 build 的选期口径一致** —— 两边都用**按日期倒序**。
早先 prep 用 `sorted()[::-N]`、build 用日期倒序 → 4 期漏了工作单，返工重派。

### ⚠️ 本地与线上可能不同步
`data/` 里目前有 115 期的抓取数据，但**只译完 32 期** → build 出来就是 32 期。
这是对的：**新期翻译完才上线**。不要为了「凑数」把没译文的期放上去（会出现空中文）。

## 签名（必须带，否则 `400 {"error":"invalid signature"}`）

```
H = md5_hex
bodyStr = "" (GET) 或 JSON.stringify(body)      # 紧凑 JSON，无空格
fullUrl = path + "?" + urlencode(params)          # params 顺序=发送顺序
x-timestamp = <unix 秒>
x-signature = H(f"{ts}I*7Cf%WZ#S&%1RlZJ&C2{bodyStr}")
yy          = H(f"{quote(fullUrl)}_{bodyStr}{H(str(time_ms))}ooui")
X-Mavis-Cron-Request-Source: ui
```

- 查询参数 = `device_platform/biz_id=3/app_id=3001/version_code=22201/unix/timezone_offset/
  sys_language/lang/uuid/device_id/os_name/browser_name/user_id/op_ticket/client=web/region=cn/token`
- `token` 放**查询参数**里（不是 Authorization 头）
- 🔴 **token 权限分层**：
  - OAuth 设备码流（`client_id=mcode_tool`，scope 只允许 `agent.mcp.app agent.mcp.matrix`）
    → 能调 `/minimax-cloud/api/v1/config`，但 cron/agent 端点 **403「access token is not authorized for this endpoint」**
  - 控制台登录态 token（`localStorage._token`，浏览器里就有）→ cron 端点正常
  - 所以：**沙箱里建 cron 只能靠"用户浏览器里跑一段脚本"**（`create_cron_snippet.js` 就是干这个的）

## 🔴 GitHub Pages 引导页的四个坑（2026-10-21 踩了一晚上，务必读）

### 坑 1：连续推文件会把 build 连环取消 ⭐最坑
每次 `PUT` 一个文件都会触发一次 Pages build，**新 build 会把上一个还没跑完的 build 取消掉**。
Actions 里看到 `conclusion=cancelled`，Pages 的 `status` 就记成 **`errored`** —— 看着像构建失败，其实是竞态。
- ❌ 错误做法：看到 errored 就反复 PUT 触发重建 → 连环取消，永远 built 不了
- ✅ 正确做法：**只轮询等待**；真的连续 errored 两次才 PUT 一次重建，然后继续等
- `push_boot.py` 的 `ensure_built()` 已经这么写了，**别再改回去**

### 坑 2：`curl -X DELETE` 不是"试探"，是真删除
我为了"看看 token 能不能删仓库"跑了 `curl -X DELETE` → **HTTP 204 = 仓库真被删了**。
**⇒ 验证权限只能用 GET/HEAD。要测写权限就 PUT 一个无害文件，测删权限别在真仓库上测。**

### 坑 3：Pages 首次开启用 POST，不是 PUT
- `POST /repos/{owner}/{repo}/pages` = 新建
- `PUT  /repos/{owner}/{repo}/pages` = 更新已存在（不存在就 404）

### 坑 4：仓库被删后重建，Pages 要重新开
删仓库会把 Pages 一起带走。重建后必须重新 POST 一次 pages，旧的 `html_url` 才会重新活。
**⇒ 引导页仓库也是"保护名单"级别的东西，删之前先想清楚。**
**⇒ 恢复脚本：`/workspace/nhk/restore_boot_repo.py`（建仓库+写文件+开Pages+验证）**

## 🔴🔴 注音/生词/句型整体错位（2026-10-22 修，easy 版的坐标基准 bug）

**症状**：easy 版（易懂版）的 ruby 注音、生词 chip、句型标签跑到别的位置；
实测 **9.3% 的句型标记（g）落在本句 ja 长度之外**（完全错位）。

**根因**：`parse_text.py` 的 `parse_easy()` 里，分词时把**整段的偏移**当成了句内偏移：
```python
toks.append([s, e - s, plain[s:e]])              # ruby token：s 是整段坐标 ❌
t2, w2 = janome_seg(plain[ss:ee], ss)            # janome 分词：base_off=ss（整段）❌
```
而 `ja` 字段是**本句**（`sp`）。前端 `ja.substr(tk[0], tk[1])` 假设 tk 坐标是**句内**坐标 → 全错。
（`parse_web()` 的 `janome_seg(sp, 0)` 是对的，所以只有 easy 版出问题。）

**修法（两处）**：
1. `parse_text.py`：`toks.append([s - idx, ...])`、`janome_seg(plain[ss:ee], ss - idx)`
   （`idx` = 本句在整段 plain 里的起点，parse_easy 里已有）
2. `build_data.py`：句型标记 `g` 走 `p2j/pend` 映射表，**那是整段坐标**，
   要减 `p2j[0]`（=本句起点）才能跟 `t`/`c` 同基准：
   ```python
   off = p2j[0]
   gmarks.append([js - off, je - js, pid])
   ```
   （web 版 `p2j = range(len(sp))` → `p2j[0]=0` → 减了也不变 ✓）

**⭐ 关键认知：一个 cue 里有三套坐标，t / c / g 必须全部是「相对本句 ja」**：
- `t` = 分词（逐词拆解 + ruby 定位）
- `c` = 生词标记（build_data 从 t 派生）
- `g` = 句型标记（走 p2j/pend 映射，**最容易漏改**）

**⭐ 已加自动闸门（build_data.py 末尾 check_coords）**：
- 断言①：每个 token 切出来的字必须和 ja 对应位置一致
- 断言②：t/c/g 标记不得越出本句 ja 长度
- **不过就 exit 1**，且 build 现在是**事务性**的：build 前备份 `subs/`，
  自检失败自动回滚 → 坏文件不会留在 `site/app/` 里
- ⇒ cron 跑 `update.py --build` 时坐标一错就会失败，不会部署坏版本

## 9. 🔴 普通版原速音声（2026-10-22 打通，v1.9）

## 10. 🔴 原生播放的三个真 bug（v1.9 修，网页版测不出来）

**网页版全绿 ≠ 原生没问题**：网页走 `<audio>` 的 `currentTime*1000`（毫秒），两边一致；
只有**原生**路径会暴露。

1. **自动滚动被自己的守卫卡死**
   - `behavior:'smooth'` + 200ms ticker → 动画反复重启 → 永远到不了目标
   - 程序滚动**也触发 scroll 事件** → 刷新了「用户滚过」标记 → 2.5 秒守卫生效
   - 修法：绝对目标 + `behavior:'instant'`（`'auto'` 在 CSSOM 里是「听 CSS 的」）；
     程序滚动时置 `autoScrolling` 标志，scroll 事件里跳过
2. **进度条被 ticker 抢 value**
   - `updateTime()` 每 200ms 重写 `$('#seek').value` → 手指还按着就被拽回去
   - 修法：`isSeeking` 标志（pointerdown → true / pointerup → false），拖动期间不写 value
3. **滚动/进度条要真拖动**
   - `touch-action:none`（手指划动别被 WebView 当滚动手势吃掉）

## 21. 🔴🔴 列表排序：用户以为「停更」的那个 bug（2026-10-25 修）

**症状**：用户打开 App，首页第一条是 **2026-10-21**，最新的一期（10-23）排在**最后** ⇒ 看着就是「没自动更新」。

**根因**（不是重复 id，是**顺序**）：`build_data.py` 拿 `episode.json` 的 **time 原始字符串**直接排序：
```python
eps.sort(key=lambda e: str(ep.get("time","")), reverse=True)   # ❌
```
而 NHK 的 time **格式不统一**：
```
"2026-10-22 20:15:00"   ← 带横杠
"20261022T201500+0900"  ← 紧凑 ISO（另一条链路抓的）
```
⇒ **字符串比较**：`'2026-10-21' > '20261022'`（因为 `'-'` < `'1'`）⇒ 新一期被甩到最后。
⇒ 而且**不报错**（没有重复 id，只是顺序反了）⇒ 极难发现。

**修法**（三层）：
| 层 | 做法 |
|---|---|
| ① 解析 | `ep_sort.py`（**唯一权威**）：时间一律解析成 `(YYYYMMDD, HHMM)` 数字元组，格式变了也不怕 |
| ② 存量 | `scripts/fix_episodes_order.py`：重排 + 重编 `no`（1..N）（**不重跑 build_data** —— 那会丢掉本地没有源的几期） |
| ③ 闸门 | `scripts/check_site_consistency.py` 加了「必须按 (date,time) 严格倒序 + no 连续」 |

🔴 **闸门必须能抓到那个坏**（反向验证过：造一份「10-22/10-23 挪到最后」的坏样本 ⇒ 闸门 exit 1）。

🔴 **首页是按数组顺序渲染的**（`EPISODES.forEach`）⇒ 数组顺序错了 = 用户看到的错了。

> 这一节是**发版流程**的权威说明。cron / 人工发版都只认 `work/deploy_nhk.sh`（prepare / finish）。
> 三道闸门**已经接进脚本**了 ⇒ 日常流程自动生效，**不需要人记得**。

### 29.1 站点配额：每次部署完**立刻删旧站**（四道闸门）

**今天的事故**：从 v1.24 到 v1.29 连发 **6 次**，每次都新建站点节点、**从不删旧的**
⇒ 50/50 配额吃光 ⇒ 部署被 `ENTITLEMENT_LIMIT_EXCEEDED` **硬拒**（当天的活全卡在这）。

**规矩**：
```
mcode 每次部署都新建节点 ⇒ 配额 50 ⇒ 一天不删就 +1
⇒ 每次部署成功后**立刻**删掉上一版节点
⇒ 只留「现役 1 个（引导页指向的）+ 永久兜底 1 个（vkwwuh9wgkzo0，冻结）」
```
🔴 **兜底站 `vkwwuh9wgkzo0` 永不删、永不 redeploy**（APK 的 `Config.SITE_URL` 写死它 ⇒ 换域名就白屏）。

**四道闸门**（`scripts/site_quota_guard.py` 内建，缺一不可）：
| 闸门 | 判据 | 为什么 |
|---|---|---|
| ① | 保护清单 `status ≠ ACTIVE`（且不是引导页当前指向的站） | 现役站永远不删 |
| ② | `frozen ≠ true` | 兜底站 / 音频源站冻结 |
| ③ | **现役 APK 的 classes.dex + assets 里没有该域名** | 别的 APK 可能编译了它当兜底 ⇒ 删了那些用户白屏 |
| ④ | **引导页 version.json + 站点源码（cdn.js / links.js / data/*.js）零引用** | 还有引用就删了 ⇒ 用户跳 404 |

**命令**（唯一实现 = `scripts/site_quota_guard.py`）：
```bash
python3 scripts/site_quota_guard.py check      # 部署**前**体检：配额 + 「只留 2 个」不变量
python3 scripts/site_quota_guard.py register --node auto --domain <新域名> --ver <ver>
python3 scripts/site_quota_guard.py plan       # 算该删哪些（打印精确的 drive files delete 命令）
python3 scripts/site_quota_guard.py apply      # 能删就删（删完验 404）；没权限就落盘待办
python3 scripts/site_quota_guard.py verify     # 该 404 的 404，现役 + 兜底仍 200
```
🔴 **删站是权限活**：平台只给部分会话 `drive files delete` 权限
⇒ 本脚本**默认只打印命令**（落盘 `work/pending_site_deletes.txt`）
⇒ **没有 drive 权限的会话（`session.mode=new`）清不了配额** ⇒ 配额清理必须由有权限的会话做。
🔴 `drive files search` 会返回**已删节点的缓存索引** ⇒ **别信它**，用 `curl` 判 404。

### 29.2 缓存版本：APP_VER / CACHE / ver **必须同号**

**症状**：用户手机上「我更新了，但内容还是旧的」。
**真因**（不是玄学）：
```
app.js 的 subUrl()：字幕 URL = subs/xxx.js?v=APP_VER
sw.js：预缓存桶名 = nhk-easynews-vNN
⇒ 这两个号不同步 ⇒ Service Worker 的 stale-while-revalidate **先返回旧字幕**
⇒ 而且 update.py --build **从来不调升版脚本** ⇒ 日常管线根本不升版本号
```

**修法**（唯一实现 = `scripts/bump_content_ver.py`，闸门 = `scripts/check_cache_ver.py`）：
```
scripts/bump_content_ver.py    写四处：version.json.ver / app.js.APP_VER / sw.js.CACHE / index.html 的 ?v= 戳
scripts/check_cache_ver.py     读三处：必须同号；读不到 / 不同号 ⇒ exit 1
```
🔴 **升版规则**：按**内容指纹**（`data/*.js` + `subs/*.js` 的 md5）升
⇒ 内容变了才升（字幕变了必须升，否则用户拿旧字幕）⇒ 没变不升（用户不必白下 200KB）。
🔴 **接进 prepare**：`work/deploy_nhk.sh prepare` 会自动
`bump_content_ver.py` → `check_cache_ver.py --dir site/app` → （复制后）`--dir deploy_site`；
**finish 阶段**还会做**线上**核查 `check_cache_ver.py --url <新站>` ⇒ 「最后一公里」也验。

🔴 **顺带修的坑**：`CACHE` 每次发版都换名 ⇒ SW 的 activate 会删掉「除当前桶外所有桶」
⇒ 用户「⬇下載」存好的**音频会被连坐清掉**（墨水屏设备流量敏感）
⇒ 现在音频单独存 `nhk-easynews-media` 桶（**永不改名**），外壳预缓存才用 `CACHE`。

### 29.3 平台注入：「剝完再部署」**去不掉 token**（查清了的結論）

**事实**（2026-10-25 实测）：
```
① 线上 index.html 的响应头是 OSS 静态对象头，Content-Length = 17617
   = 本地剥干净的 16094 + 平台注入的 1523 字节
   ⇒ **注入后的文件被存进了 OSS**（不是每次请求时拼的）
② 平台自己的 404 页面（另一份 HTML）**没有**注入 ⇒ 不是「所有 HTML 都过一遍」
③ 兜底站（更早部署的）也有注入，token 里带的是**它自己**的 node_id ⇒ 每次部署注一次
```

**结论**：
```
「剝完再重新部署」只会换一个**新 token** + 新域名 + 多一个要删的站 ⇒ **去不掉 token**
真正能去的只有三条路：
  (a) 平台侧关掉「网站分析注入」（控制台开关；沙箱够不着）
  (b) 覆盖 OSS 上已存的那个对象（需要 drive **写**权限；本项目只有 list/search/delete）
  (c) 搬到我们自己控制的托管（GitHub Pages）—— 大改，暂不做
```

**我们能保证的（每条都有判据，脚本 `scripts/check_live_inject.py` 线上实测）**：
```
✅ 拦截器在（head 最前面 `var BLOCK = 'agent.minimax.cn'`）
✅ 运行时兜底在（platformInjectGuard：把注入脚本/悬浮球从 DOM 摘掉）
✅ 悬浮球不可见
✅ **外发 0 条**（浏览器实测：23 个请求，0 条到 agent.minimax.cn）
⚠️ token 仍在源码里（平台行为，拦截器已让它失效）⇒ 记 WARN，不记 FAIL
```
🔴 **不要**为了「去掉 token」去重新部署：那是**白烧一个配额 + 换域名 + 改引导页 + 再删一个站**。

**为什么要有它**：mcode 站每次 redeploy 都换域名 ⇒ 收藏不住 ⇒ 用户的收藏夹里需要

### 30.1 怎么同步（**在推引导页之后**）
```bash
# 🔴 顺序：③ 推引导页（更新仓库 version.json 的 site = 现役站）→ ⑥ 同步 Pages
python3 scripts/check_pages_sync.py --before --src /workspace/nhk/deploy_site   # 护栏①
python3 scripts/sync_pages.py        --src /workspace/nhk/deploy_site           # 同步本体

```
⇒ **已经接进 `work/deploy_nhk.sh finish` 的第 ⑥ 步**（日常流程自动跑，不用人记得）。

🔴 **源目录必须是「本次部署的那份」= `deploy_site`**，不是 `site/app`
（`site/app` 可能已被别的进程改过 ⇒ 推上去就不是线上那版了）。

### 30.2 两道护栏（**缺了就会出静默事故**）
```
护栏① --before：源目录必须**具备线上已发布版本已有的全部能力特征**
   ⇒ 源比线上旧 ⇒ 直接停，不许推
   （真事故：旧 sw.js 没有「离线预热」⇒ 一次同步就把断网可看字幕的能力抹掉了；
     旧 sw.js 没有 MEDIA 音频桶 ⇒ 用户存的音频每次发版被清空）
护栏② --after：线上副本必须
   · 能力特征齐全（MEDIA / warmSubs / DATA_PRELOAD / 拦截器 / 运行时兜底）
   · **APP_VER == CACHE**（用唯一实现 scripts/check_cache_ver.py 验）
   · MEDIA_BASE 含**现役站**（读仓库的 version.json 判）
   · **期数与源目录一致**（防「线上还是旧的」）
```

### 30.3 三个必须记住的事实
```
① **Pages 版是 site/app/ 的投影，不是独立的一份代码**
   ⇒ 改动**一律先改 site/app/**，再同步过去
   ⇒ **不要直接改 Pages 那份**（下次同步会覆盖回去）
② **升版规则**：Pages 副本的号 = max(线上+1, 源目录+1)（sync_pages.py 内部）
   ⇒ 不升的话 Service Worker 直接返回旧字幕 ⇒ 用户看不到更新
③ **已知限制**：Pages 版的「⬇ 存本集音频」不可用
   （Service Worker 不缓存**跨源**音频 ⇒ 音频在 mcode 站，是另一个 origin）
   ⇒ 只有 App 版能存音频；网页版正常使用不受影响
```

### 30.4 🔴 顺带补上的一个真缺口：`sw.js` 变了也必须升版
`scripts/bump_content_ver.py` 的**内容指纹**现在把 `sw.js` 也算进去了（哈希前抹平 CACHE 那行）：
```
SW 的注册 URL 是 `sw.js?v=APP_VER`
⇒ sw.js 本身改了而 APP_VER 没升 ⇒ 注册 URL 不变
⇒ 浏览器可能继续用**缓存里的旧 sw.js** ⇒ 新加的离线预热（4.6MB）到不了用户手里（且不报错）
⇒ 所以 sw.js 变了也算「内容变了」⇒ 必须升号
```

## 31. 🔴🔴 日更零配额架构 —— 内容走 Pages，音频走 mcode + 清理闭环（2026-10-25 新增，22:5x 改）

### 31.1 真事故（不是假想）
```
2026-10-25 当天：从 v1.24 部署到 v1.29 **共 6 次**（同日连发）
⇒ 每次 website_deploy 都**新建站点节点**、从不删旧的
⇒ 50/50 配额吃光 ⇒ 部署被 ENTITLEMENT_LIMIT_EXCEEDED **硬拒**
⇒ 而「部署」这个动作在配额满时是**零产出**（连站都没建出来）
⇒ 排查了半天以为是部署脚本坏了
```
**根因**：`website_deploy` 每次都新建节点，不覆盖旧的 ⇒ **迭代次数 = 占位次数**。

### 31.2 核心洞察：NHK 每天变的是「内容」，不是「站」
```
⇒ 内容（字幕/词库/语法/前端）→ **GitHub Pages**
   · 一个仓库 = 一个站点 ⇒ **推 50 次还是 1 个** ⇒ **零 mcode 配额占用**
   · 地址永不变 ⇒ 用户收藏不失效
   · 已发布站点 ≤ 1GB（硬）/ 仓库 ≤ 1GB / 单文件 ≤ 100MB / 构建 10 分钟
   · 实测：仓库 54.6MB（占 5.3%）、最大文件 5.9MB、最近构建 12 秒 ⇒ 余量巨大
⇒ 音频 → **mcode**（实测 github.io 拉 790KB 要 23~48 秒，mcode 只要 0.28 秒
   ⇒ 差 60 倍 ⇒ 音频搬 Pages 等于让用户没法听）
   ⇒ 音频必须留 mcode（单站 200MB ⇒ 一个音频站能装约 148 期 ⇒ 体积根本不是瓶颈）
```
**日更的正常路径因此是**：
```
① 内容变了 ⇒ **只推 Pages**（零配额）—— `bash work/deploy_nhk.sh pages`
② 有新增音频 ⇒ 就发一次 mcode 站 ⇒ **发完立刻把旧站写进待删清单** ⇒ 清理 cron 删（净增 0）
```

### 31.3 唯一实现：`scripts/daily_publish.py`（**配方不许写两遍**）
```bash
python3 scripts/daily_publish.py --plan                # 只看决策
python3 scripts/daily_publish.py --sync-pages           # 同步 Pages（零配额）
python3 scripts/daily_publish.py --need-audio-deploy   # exit 0=要发 / exit 3=不要发
python3 scripts/daily_publish.py --mark-audio-deployed --domain <域名>
```
🔴 **判据落在「事实量」上，不是表示量**：
```
内容指纹 = md5(data/*.js + subs/*.js + app.js + style.css + index.html + config.js) 的集合再哈希
音频指纹 = md5(media/{slow,fast}/*) 的集合
⇒ 「内容变了」不是看有没有新文件，是看**每个文件的 md5**（改一个字也算变）
⇒ 「音频有新增」是看**集合差**，不是看文件数
```
🔴 **发布节奏**（在脚本里，配方只此一处 → `scripts/daily_publish.py` 的常量）：
```
新增音频 ≥ **1 期**  或  距上次发音频站 ≥ **1 天**  ⇒ 就发 mcode 站
⇒ **即「NHK 出了新一期 ⇒ 当天就发」** ⇒ App 里当天能看到新一期（App 走 mcode 站）
```
🔴🔴 **2026-10-25 22:5x 从「攒批 10 期 / 7 天」改成「1 期 / 1 天」—— 算过账才改**：
```
每次 website_deploy 传的都是**全量**（44 期音频 59MB + 静态 4.5MB ≈ 64MB）
⇒ **跟攒多少期完全无关** ⇒ 「攒批」唯一收益 = 少发几次 = 给清理 cron 留缓冲
⇒ 代价却是实打实的：**用户最多等 7 天才看到新一期**
⇒ 改成「每天发」+「清理闭环」后，配额**稳态一样是 2~3 个位**：
   发完 ⇒ 旧站写进 **共享仓库 `pending-deletes.json`**
        ⇒ 20:00 清理 cron（agent=Mavis, mode=new ⇒ **有 drive 删站权限**）捡起来删
        ⇒ 回写 `protected-sites.json` 的 status=DELETED
⇒ 收尾 cron 的 prompt 本来就会读 `pending-deletes.json` ⇒ **接口早就有了，只是没人写**
```
🔴 **配额保险**（`MAX_PENDING_DELETES = 3`）：
```
待删站**还活着**的个数 ≥ 3 ⇒ **停发 mcode 站**（Pages 照常同步，零配额）
⇒ 理由：清理 cron 万一连着几天没跑，站会一天天堆 ⇒ 撞 50 上限 ⇒ 部署直接被拒
⇒ 判据落在**事实量**上：读 `pending-deletes.json` ⇒ 逐个 curl 判活 ⇒ 只数「还活着」的
   （清单里已死的 404 不算积压）
```
🔴 **登记动作 = `scripts/site_quota_guard.py export-pending`**（`deploy_nhk.sh finish` 第⑤步自动调）：
```
本会话常常**没有 drive 删站权限** ⇒ register/plan/apply 只写**本地** work/site_registry.json
⇒ 而清理 cron 跑在**另一个沙箱**（mode=new）⇒ **本地文件它永远看不到** ⇒ 闭环断一半
⇒ 所以必须把待删清单写进**永久地址**上的 `pending-deletes.json`（清理 cron 的 prompt 本来就会读）
⇒ 导出前会逐个 curl 判活 ⇒ **已死的不导出**（不浪费清理 cron 的额度）
⇒ 清理 cron 删完：从 sites[] 移除 + 把 protected-sites.json 里 status 改成 DELETED
```

```
⇒ 同族老教训：「反向验证的前提是反例真的造出来了」
```
🔴 **写这条时踩到的真 bug**：`--need-audio-deploy` 分支忘了 `return`
⇒ 退出码被 `main()` 末尾的 `return 0` 覆盖 ⇒ **「不要发」被当成「要发」**
⇒ 后果正好是本节要防的：日更白占一个部署位。
⇒ **教训：判据的「返回结论」和「退出码」必须同一处产生**，不许一个地方判、另一个地方转述。

## 32. 🔴 共享仓库（`tlv-creator/nhk-easy-news`）—— 沙箱会重置，项目不能只活在一个沙箱里

### 32.1 为什么必须进共享仓库
```
🔴 **沙箱会重置，项目会没** ⇒ 代码/手册/配方不能只活在 /workspace
⇒ 源码进共享仓库 ⇒ setup_env.sh 自动从那里恢复（**用 `cp -r src/. dst/`，别写成 `cp -r src dst`**
   —— 后者会把 src 变成 dst 里的一个子目录 ⇒ 路径全错）
⇒ 手册也是：线上 `nhk/手册.md` = 本地 `手册.md` 的**同步副本**（**配方不许写两遍**）
```

### 32.2 🔴「防双部署」闸门（`work/deploy_nhk.sh prepare` 里）
```
期数表 + 最新一期字幕的 **md5** 与现役站相同 ⇒ 直接 exit 1 拒绝部署
⇒ 为什么：两个 cron 同时跑 ⇒ 各发一版 ⇒ 配额翻倍 + 引导页被后一个覆盖
⇒ 判据落在 **md5**（事实量），不是「有没有新文件」（表示量）
```

### 32.3 🔴 列表排序修复时**只排数组、不动 `no`**
```
`ep.no` 是生词本关联用的编号（用户已存的生词靠它指回期数）
⇒ 重排数组时如果把 `no` 一起重编 ⇒ 用户存的生词会指错期
⇒ **只调数组顺序，`no` 一律不动**
```

### 32.4 推送纪律（`scripts/push_files.py`）
```
① 基线永远取**线上最新**（不拿本地副本）⇒ 409 时重取重试，不覆盖别人
② 回读**逐字对账**（不是只看 API 返回 ok）
③ 只推指定文件，不整份覆盖
④ 推共享文件前**先拉线上版对比**（本地是 99KB / 线上曾是 10KB 的「重建版」）
   ⇒ 线上版有 3 条本地没有的真事实（cp -r src 坑 / 防双部署闸门 / ep.no 不动的坑）
   ⇒ **补进本地再推**，不许直接覆盖丢掉
⑤ **同一个文件两处存在 ⇒ 有一处是陈旧的**（本次就踩到：线上手册停在 10-24 的「缺口」，
   而那些缺口 10-25 早已解决 ⇒ 线上手册是过时的）
```

### 33.2 🔴 必须知道的一个等待：首次点词要等词库
```
现象：第一次点句，弹窗**等了 91~122 秒**才出；第二次访问 **2.8 秒**（32× 加速）

⇒ 用户真实感受：点第一个词可能等一会儿，读两行之后基本就秒开了
⇒ **App 版不受影响**（词库在 APK/内容站里，不走 github.io）
```

### 33.3 🔴 写网页版测试时踩的三个坑（都曾让我误判「站点坏了」）
```
① **subs 是异步加载的** ⇒ 不能用固定 sleep 等字幕
   ⇒ 必须 `wait_for_selector('.cue', timeout=30000)`
   ⇒ 固定 sleep 3000 → cues=0 → **假红**
② **选择器要按真实 DOM 写**：
   句子 = `.cue`（不是 .sen/.sent）｜详解弹窗 = `#pop .pop-card`（不是 [class*=pop]）
   ｜版本按钮 = `#verBar button.vb`｜复制按钮 = `[data-act="sp-copy"]`（不是 id）
   ｜全局 = `window.__EPISODES__`（不是 window.EPISODES）
   ⇒ `#verBar` 在**首页本来就该隐藏**（进某期才出现）⇒ 首页量它 = 假红
③ **元素会被重渲染** ⇒ Playwright 句柄会「not attached to the DOM」
   ⇒ 用 `pg.evaluate("()=>document.querySelector('.ep-item').click()")` 而不是句柄 click
⇒ 通则：**「测试红」先怀疑「测试写错」**，再去怀疑「站点坏了」
```

## 34. 🔴🔴 2026-10-25 晚：Pages 同步的两个真 bug（都差点让线上和本地不一致）

### 34.1 🔴🔴 「Pages 推的是 deploy_site（旧的），不是权威目录 site/app」
```
现象：我改了 site/app（给 44 期挂上语法新格式 blk）⇒ 跑 pages 同步
     ⇒ 线上 APP_VER 升到 v36（对）但 **subs 的 blk = 0**（错）
     ⇒ 现象：本地 HTML 版有新格式，网页版没有 ⇒ **两边不一致**
根因：**有两个「源」**
     ① site/app    = **权威目录**（内容真身）
     ② deploy_site = 部署产物（prepare 的第①步 `rm -rf && cp -a site/app deploy_site` 生成的）
     ⇒ 我跳过了 prepare ⇒ deploy_site 还是旧的 ⇒ 推的是旧内容
🔴 **手册 §30.3 写的是「改动一律先改 site/app 再同步」—— 但实现里同步用的是 deploy_site**
     ⇒ **手册与实现不一致 = 必踩**
✅ 修法（已落地 `scripts/daily_publish.py`）：
     sync_pages() 第一步 = `sync_deploy_site()`（自动 cp -a site/app → deploy_site）
     ⇒ **推之前强制同步** ⇒ 不可能推旧
     ⇒ 并打印两个指纹（site/app bb381e2351 / deploy_site 37ea567ab5）⇒ 不一致一眼看出来
```

### 34.2 🔴🔴 「本地状态说已同步」是假的 ⇒ 跳过判据必须查**线上**
```
现象：上一轮推错了（推了旧 deploy_site），但状态文件 `pages_synced_sha` = 源目录指纹
     ⇒ 下一轮判「内容没变 ⇒ 跳过」⇒ **错误状态被固化** ⇒ 再也推不上去
根因：**「我算过指纹」≠「线上有这个内容」** ⇒ 判据落在**本地**就等于自证
✅ 修法：跳过判据改成 **逐文件比对线上 blob sha**（`remote_matches_source()`）
     ⇒ 线上与源目录不一致就推 ⇒ 判据落在**线上**这个事实上
     ⇒ 本次抓到：45 个文件内容不同（44 期 subs + 1）⇒ 正是要推的那些
🔴 同族通则：
   > **「我记录的状态」不能当判据** ⇒ 判据要落在**被作用的那个对象**上。
   ⇒ 同款：缓存「已写入」标志、清单「已提交」标志、锁「已持有」标志 —— 都可能撒谎。
```

```
### 34.5 🔴 一个反复咬我的计数坑
```
`grep -c '"blk"' file` 数的是**行数**，而 subs 是**单行文件** ⇒ 永远返回 1
⇒ 误判「线上 blk 只有 1 处」⇒ 差点去查假故障
✅ 数出现次数要用：`grep -o '"blk"' file | wc -l`
⇒ 同族：**「计数器口径」要跟被测的东西对上**（行 vs 次 vs 条）

### 34.6 🔴🔴 闸门自指：连注释里都不许出现完整字面量（今天连踩两次）
```
事故①：`scripts/pack_html.py` 里写 `re.compile(rb"-----BEGIN CERTIFICATE-----")`（用来扫凭据）
      ⇒ 源码包里就有这个连续串 ⇒ **凭据闸门把脚本自己判成凭据** ⇒ 发布被拦
事故②：同一个脚本里的签名口令字面量 ⇒ 同样自指
✅ 正解（标准做法，闸门自己早就在用）：**拆开构造**
   `_PEM_H = b"-"*5 + b"BEGIN "` ／ `_FTR = b"-"*5` ／ 口令 `b"news" + b"2024"`
   ⇒ 源码里没有连续字面量，**扫描能力完全不变**（实测：证书/私钥/口令 4/4 仍被抓）
   ⇒ 🔴 **注释里也不许写完整字面量**（我第一版改了代码、注释还留着 ⇒ 照样被拦）
⇒ 通则：**写「扫描某类危险物」的脚本时，危险物的样子必须拆开写** ⇒ 否则它自己就是那个危险物
```

### 34.7 🔴 闸门「检查」在「刷新」之前 ⇒ 扫的是上一轮的产物
```
事故：prepare 的第①步扫 `deploy_site` + `work/src_slim`
     ⇒ 而 work/src_slim 是**上一轮**留下的副本（第③步才刷新它）
     ⇒ 今天 pack_html.py 已修好，但 src_slim 里还是旧副本 ⇒ **误报当前有问题**
     ⇒ 附带更糟：**本轮新引入的凭据要等下一轮才被抓**（滞后一轮）
✅ 修法：第①步**只扫 deploy_site**（当轮产物）；src_slim 由**第③步之后**那次检查负责
   （那次才是当轮的）
⇒ 通则：**闸门扫的必须是「当轮产物」** ⇒ 顺序依赖要在闸门里显式处理
⇒ 同族：先检查后生成的流水线，检查到的是上次的残留
```
